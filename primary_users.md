# 1. Primary Users (High Interaction Level)

Primary users are the core operational engine of the Cultural/Drama Club Management System. They interact with the platform on a daily basis to run internal club mechanics, handle facility bookings, orchestrate rehearsals, and process the external data pipelines generated by secondary (prospective members/regulatory bodies) and tertiary (sponsors/external institutions) stakeholders.

### Club Members (Performers, Cast, Crew)
Active, verified members of the club who rely on the platform to maintain sync across intensive artistic and technical production lifecycles.
*   **Typical Activities:** Tracking personalized call-times, booking available rehearsal infrastructure, self-assigning to event sub-committees, and updating internal performance portfolios.

### Core Members & Event Organizers (Secretary, President, Treasures, Directors)
The management layer responsible for the operational throughput, administrative oversight, and external boundary management of the organization.
*   **Typical Activities:** Processing inbound member applications, drafting compliance-ready event blueprints, allocating budgets, scheduling multi-phase rehearsal timelines, and linking external promotional material to active public showcase streams.

### Club Administrators & Maintainers (Systems Admin, Technical Leads)
The governance and infrastructure tier responsible for data integrity, Role-Based Access Control (RBAC), security compliance, and lifecycle system roll-overs.
*   **Typical Activities:** Auditing permission groups, executing annual board handovers, maintaining active database indexing, and running data-retention archival scripts to optimize system storage.

# SMART User Stories

## Epic 1: Membership Lifecycle & Pipeline Processing (Inward Integration with Amit's Scope)

### User Story 1.1: Standardized Audition Evaluation & Roster Promotion
*   **As a** Club Secretary,
*   **I want to** view a consolidated dashboard of inbound new-member applications, screen their uploaded video portfolios, and change their profile status from "Auditioning" to "Active Member" with a single click,
*   **So that** accepted applicants automatically inherit base internal platform permissions within 60 seconds without manual account recreation.
*   > **SMART Validation:**
    *   **S (Specific):** Targets the core administrative approval funnel and automated permission inheritance.
    *   **M (Measurable):** Permissions must execute system-wide within a **60-second window**.
    *   **A (Achievable):** Leverages conditional relational database writes changing user role IDs.
    *   **R (Relevant):** Solves Amit’s "Observation 1: Manual Membership Management" and connects seamlessly to his New Member story loops.
    *   **T (Time-bound):** Tied directly to processing applicants during the structural phase of early-semester recruitment.

## Epic 2: Facility Coordination & Scheduling Guardrails (Internal Mechanics)

### User Story 2.1: Multi-Entity Calendar Conflict Validation
*   **As a** Regular Club Member (Performance Lead),
*   **I want to** select an open rehearsal hall on the live interactive calendar and secure a maximum 2-hour practice slot for my team up to 7 days in advance,
*   **So that** the backend automatically blocks any overlapping reservation attempts and prevents physical room-clashing friction.
*   > **SMART Validation:**
    *   **S (Specific):** Automated calendar intersection checking for rehearsal spaces.
    *   **M (Measurable):** Restricts reservations to a strict **2-hour maximum cap** and **7-day advance booking window**.
    *   **A (Achievable):** Implemented using time-range overlap query parameters in the database booking engine.
    *   **R (Relevant):** Addresses the club's core operational pain point of chaotic, uncoordinated rehearsal overlaps.
    *   **T (Time-bound):** Calendar states must validate and display the locked reservation instantly upon form submission.

### User Story 2.2: Contextual Activity Call-Time Feeds
*   **As a** Regular Club Member,
*   **I want to** view a chronological, personalized dashboard feed displaying only the specific event call-times, rehearsal shifts, and script changes assigned to my profile,
*   **So that** I am notified of schedule changes instantly without scanning noisy, unrelated club-wide notifications.
*   > **SMART Validation:**
    *   **S/M:** Specific to assigned individual shifts, measured chronologically by dates and explicit location tags.
    *   **A/R:** Achieved by filtering the global schedule table against the logged-in User ID; directly solves Amit's "Observation 2: Scattered Communication."
    *   **T:** The user feed must refresh and push automated alerts within 3 minutes of an organizer publishing a scheduling modification.

## Epic 3: Governance, Compliance, & External Delivery (Outward Integration with Amit & Devi)

### User Story 3.1: Standardized Event Proposal Compilation
*   **As an** Event Organizer,
*   **I want to** populate a mandatory, pre-validated digital template (covering venue lock, inventory dependencies, budget tallies, and safety plans) to submit directly to the Student Affairs pipeline,
*   **So that** the system blocks submission if required fields are blank, preventing rejection cycles from incomplete documentation.
*   > **SMART Validation:**
    *   **S (Specific):** Enforces field-level validation rules matching institutional templates prior to database saves.
    *   **M (Measurable):** Validates 100% of required fields before opening up the "Submit to Faculty" trigger.
    *   **A (Achievable):** Managed via frontend form validation patterns and structured database validation models.
    *   **R (Relevant):** Directly solves Amit's Regulatory Body Pain Point 3.1 ("Receives incomplete or inconsistent event proposals").
    *   **T (Time-bound):** System logs a time-stamped digital receipt the moment the completed pack crosses the compliance barrier.

### User Story 3.2: Sponsor Ad-Asset Insertion Dashboard
*   **As a** Core Treasurer,
*   **I want to** access pending external ad requests, review verified payments, and bind the sponsor's uploaded promotional assets to our public-facing event booking cards,
*   **So that** promotional banners go live automatically on the public site the instant the event ticket tier opens.
*   > **SMART Validation:**
    *   **S/M:** Specific to joining external ad assets to target public event structures; measured by automated publication syncing.
    *   **A/R:** Achieved through relational database joins mapping Devi's Sponsor Asset IDs to active Event Table entries; resolves Devi's Sponsor Pain Point 3.1.
    *   **T:** Banners must dynamically render on the frontend within the exact activation hour of the public ticketing gate launch.

## Epic 4: Infrastructure Security & Annual Transition Management (System Governance)

### User Story 4.1: Automated Role De-escalation & Key Revocation
*   **As a** System Maintainer,
*   **I want to** initiate a batch-update script at the close of an executive term that transitions graduating board profiles down to "Alumni" status and clears all access keys,
*   **So that** legacy administrative access is completely locked out across the platform within a strict 24-hour governance window.
*   > **SMART Validation:**
    *   **S (Specific):** Role-Based Access Control (RBAC) batched transition utility.
    *   **M (Measurable):** Complete data access revocation executed safely across target profiles within **24 hours**.
    *   **A (Achievable):** Handled via administrative cascading update requests editing permissions fields inside the global users table.
    *   **R (Relevant):** Mitigates technical risk, prevents cross-semester security leaks, and guarantees operational integrity.
    *   **T (Time-bound):** Bound structurally to execute at the precise conclusion of the annual club election cycle.
